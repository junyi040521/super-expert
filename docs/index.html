01它治的是什么病

不是「不会做」，是做完了说不清：报告写着「已修复」，但没人能复算； 检查表 902 项全绿，可那个数字在全库只出现过一次；CI 红了，红在装环境，被测物一行没跑。 这些情况下系统都正常退出，只是给出了错误结论。

一个从不否决的闸门，在报告里和没有闸门完全一样。 所以本项目的验收标准不是「有多少条检查」，而是每条判据是否真的红过。

02五级阶梯：每一级防一种特定的自欺

级别问的问题怎么判定防的自欺
L1判据完备吗13 条判据都写了「什么情况下这条必须红」只有标准，没有触发条件
L2判据能被证伪吗拿假闸门喂它，必须抓得住（falsify.py）永远不会红的断言
L3在真实场景里红过吗案例库 ≥3，每个案例四段齐全（发生了什么 / 判据 / 证据 / 复验）只在夹具里成立
L4在真实仓库上红过吗真仓跑出来的变红记录 ≥1，逐条对上判据纸上判据
L5覆盖账诚实吗分母闭合 + 每条 covered 有变红记录 + text-only ≤ covered把「提过」算成「做到」

L1–L3 在仓库内可独立验证，CI 跑 --grade-l3；L4/L5 需要外部证据，缺了是 UNKNOWN，不是红——让 CI 因为「没有私有文件」变红，会训练所有人忽略红。

05四个案例：都是真拦下来的误判

编号发生了什么打脸的是
001状态码 200 但响应体 0 字节，被读成「通了」，据此给出一个根本不可能成立的方案任何数字要有两个独立口径
002CI 红了，但红在 setup-python 安装，被测物一行没跑（skipped 不是 failed）判据要指向被测物
003上传「成功」、9 个文件字节全对、CI 全绿，但提交历史被压平（2 个只剩 1 个）判据必须能当场变红
004名叫「超时不算通过」的断言，用 sleep(30) 配 timeout=120——30 秒就正常返回了，超时分支一次没进过本仓库自己的判据
前三例打脸的是别人的判据，004 打脸的是这个仓库自己：它已经拿着最高等级，名下却有一条从没变红过的断言。 修复后断言 4 → 6，falsify --selftest 62.8 秒 → 5.9 秒（原来两个方向各白等 30 秒）， 顺带修掉根因：shell=True 时只 kill 子进程，孙进程还占着 stdout 管道，把 1 秒超时拖成 20 秒。

06它明确不做的事

  • 不评分：不给你 0–100 分，只给「够 / 不够」和缺哪一条。
  • 不猜：读不到就说读不到，不推断意图。
  • 不联网：全部本地跑，0 依赖。
  • 不把「没查到」算通过：没条件测和测了通过，是两个状态。
  • 不替你做结论：它只回答「现在能证到几级」，剩下的判断是你的。
